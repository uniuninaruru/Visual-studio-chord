# 調査したコード進行を「全実装」するための考察

[chord-progressions-and-theory.md](chord-progressions-and-theory.md) と [niche-genres.md](niche-genres.md) で集めた進行・技法を**すべて表現可能にする**には何が必要か、現行コードを読んだ上での分析です。

**結論を先に**: 「進行データを足す」作業ではありません。**現行の型が表現できない進行が全体の半分以上**を占めており、いくつかは**データモデルの変更**を要します。ただし依存関係を整理すると、**3つの基盤変更**がボトルネックで、それを入れれば残りは素直に載ります。

---

## 1. 現行アーキテクチャの制約（実コード確認済み）

### 1.1 進行テンプレートの型が「度数の配列」

```ts
// frontend/src/music/styles.ts
majorProgressions: readonly (readonly number[])[];   // 例: [[1,5,6,4], [4,5,3,6]]
```

進行が **`number[]`（1〜7の度数）としてしか表現できません**。この1行が、調査した進行の大半を排除しています。

`[4,5,3,6]`（王道進行）は書けますが、**以下はすべて書けません**:

| 書けない進行 | 理由 |
|---|---|
| `IVM7–V7–iii7–vi7` | **和音品質を指定できない**（度数だけ） |
| `IVmaj7–III7–vi7`（丸サ） | 同上。`III7` は品質が本質 |
| `I–III7–vi` | `III7` がセカンダリードミナントであることを表せない |
| `Vaug/♭II`（ブラックアダー） | **度数7種に収まらない**（♭II）＋ **ベース指定不可** |
| `C–C/B–Am–Am/G`（トレイン進行） | **スラッシュコード不可** |
| `I–IM7–I7–I6`（クリシェ） | **同一度数の反復**で品質だけが動く |
| `♭VI–♭VII–I` | **♭付き度数が表現不可** |
| `i–♭III–♭VI–V`（Kanaria） | 同上 |
| `Faug–E♭aug`（非機能的平行移動） | 度数の枠組みそのものから外れる |

**現行で表現できるのは「ダイアトニック7度数の並び」だけ**です。品質は `HarmonyCandidateKind` の重み付き抽選で**後から確率的に決まる**ため、「この進行のこの位置は必ず `III7`」という指定ができません。

### 1.2 和音は「root + quality」の閉じた組でしか作れない

```ts
function chordCandidates(rootSemitone: number, quality: ChordQuality, ...)
  const intervals = intervalsForQuality(quality);   // 品質から音程が一意に決まる
```

`ChordQuality` は列挙型で、**音程セットが1対1で固定**されています。この設計だと:

- **テンションの組み合わせ爆発**に対応できない（`V7♭9♯11`、`Imaj9♯11`、`m7add13` …）
- **`add9` と `maj7` を同時に積めない**（前述の kawaii future bass の核心的ギャップ）

### 1.3 ベース音を指定できない

```ts
export interface ChordEvent {
  root: CanonicalPitchClass;
  inversion: number;      // ← 構成音の転回しか表せない
  notes: number[];
}
```

`inversion` は**構成音の並べ替え**です。**構成音でないベース音**（`Vaug/♭II` の ♭II、`Gaug/F` の F、`FΔ/G` の G）は指定不可能。

### 1.4 曲は「単一キー・単一モード・1ループ」

```ts
export interface GeneratorSettings {
  key: PitchClassName;   // 1つだけ
  mode: Mode;            // 1つだけ（メロディも和音も共有）
  bars: BarCount;        // 4 | 8 | 16
}
```

セクションの概念がなく、転調・複調・通作形式がすべて表現できません。

### 1.5 声部進行は「最小移動」に固定

`voicingCost` は共通音保持と最小移動を常に善とします。しかし調査では**逆を要求する例**が出ました:
- 田中秀和 `Faug–E♭aug` の**非機能的平行移動**（全音音階的）
- じんの**ベース線主導**（ベースの順次進行が先、和音が従属）
- kawaii future bass の**広い開離配置**（色彩音を上声へ）

## 2. 何を変えれば全部載るか — 3つの基盤変更

依存関係を解くと、以下**3つ**がボトルネックです。これらを入れれば残りは既存の枠組みに素直に載ります。

### 基盤A — 進行テンプレートを「構造体の配列」にする

`number[]` を、度数・品質・ベース・機能を持てる型に置き換える。

```ts
interface ProgressionStep {
  degree: number;                  // 1..7
  alteration?: -1 | 1;             // ♭II, ♯IV など（♭VI/♭VII/♯vi を表現）
  quality?: ChordQuality;          // 未指定ならダイアトニック
  tensions?: Tension[];            // 9, 11, 13, ♭9, ♯9, ♯11, ♭13
  bass?: { degree: number; alteration?: -1 | 1 };  // スラッシュコード
  role?: "secondaryDominant" | "tritoneSub" | "borrowed" | "passingDim";
  targetDegree?: number;           // V7/x の x
}

type ProgressionTemplate = {
  name: string;                    // "王道進行" / "丸サ進行"
  numeric?: string;                // "4536" — 実務者向け表示
  steps: ProgressionStep[];
  usage?: "verse" | "preChorus" | "chorus" | "bridge";  // 「サビ冒頭4小節が効く」
};
```

**これ1つで解決するもの**: 王道/小室/丸サ/カノン/循環、`I–III7–vi`、`♭VI–♭VII–I`、`i–♭III–♭VI–V`、クリシェ、経過減七、バックドア、トライトーン代理、トレイン進行、ブラックアダー。**調査した名前付き進行のほぼ全部**。

さらに `usage` フィールドは、実務者サイトが教えてくれた「**どこで使うか**」（王道＝サビ冒頭、小室＝サビ全体、カノン＝バラードのサビ）をそのままデータ化でき、後述の基盤Cと直結します。

**互換性**: 既存の `[1,5,6,4]` は `steps: [{degree:1},{degree:5},{degree:6},{degree:4}]` に機械変換できるので、**既存プリセットを壊さず移行可能**。

### 基盤B — 和音を「baseQuality + tensions[]」に分離

`ChordQuality` の列挙を増やし続ける方式をやめる。

```ts
interface ChordSpec {
  base: "major" | "minor" | "diminished" | "augmented" | "sus2" | "sus4";
  seventh?: "major7" | "minor7" | "diminished7";
  tensions?: Array<9 | 11 | 13 | "b9" | "#9" | "#11" | "b13" | 6>;
  omit?: Array<3 | 5>;            // ルートレス/5th省略
}
```

**これで解決するもの**: `maj9`（7th+9th の同時積み）、`6/9`、`m7add13`、`V13♭9`、`V7♯5`、`Imaj7♯11`、そしてブラックアダーの上部構造 `aug`。

**同時に必要な付随実装**（調査で判明した理論的制約）:
1. **アヴォイドノート回避** — メジャー/ドミナント系に自然11thを乗せない（3rdと短9度で衝突）。`♯11` に上げるか3rdを省略
2. **ボイシング縮約** — 7音スタックは13thまで21半音で演奏不能。ガイドトーン（3rd/7th）優先保持 → 5th/root省略 → テンションは1〜2個
3. **テンションは上声へ** — 13thが6thに聞こえないよう7thより上に配置

### 基盤C — セクション構造

```ts
interface Section {
  kind: "intro" | "verse" | "preChorus" | "chorus" | "bridge" | "outro";
  bars: number;
  key: PitchClassName;             // セクション毎に持つ
  mode: Mode;
  melodyMode?: Mode;               // ← 複調（中田ヤスタカ）
  melodyScale?: "diatonic" | "pentatonic" | "yonaNuki" | "niroNuki";
  progression: ProgressionTemplate;
  repeat?: boolean;                // false なら通作形式（artcore）
}
interface GeneratedComposition { sections: Section[]; /* ... */ }
```

**これで解決するもの**: セクション別進行（アニソン A/B/サビ）、転調（トラックドライバー、短3度上、しれっと転調）、複調、ペンタトニック、通作形式。

## 3. 全実装を阻む「難所」の分析

基盤A〜Cで大半は載りますが、**素直に載らないもの**が残ります。ここが本当の考察対象です。

### 難所1 — 度数体系では表せない和音がある

`Faug – E♭aug – Faug – E♭aug`（田中秀和「PUNCH☆MIND☆HAPPINESS」）は**全音音階上の平行移動**であり、機能和声の度数ラベルを持ちません。`alteration` を足しても本質的に馴染みません。

> **判断**: これは進行テンプレートではなく**「非機能的シーケンス」という別カテゴリ**として持つべきです。`ProgressionStep` に無理に押し込めず、`kind: "parallel-sequence"` のような別の生成器を用意する方が正しい。**全実装＝単一の型で全部表す、ではない**という結論。

### 難所2 — ベース線主導は生成順序が逆

じんの `i–v–vi–♯vi`、ゴスペルのトレイン、カノンの下降ベースは、**ベース線が先にあり和音が従属**します。現行は「和音を決める→ボイシングでベースが決まる」。

> **判断**: 基盤Aの `bass` フィールドで**結果としては**表現できます（各ステップにベースを明示すればよい）。ただし**自動生成**したいなら、`voicingCost` にベース順次性の報酬を足す程度では不十分で、**ベース線を先に引く生成モード**が要ります。
> **段階的対応**: まず `bass` 明示でテンプレートとして持つ（安価）。自動生成は後回しで実害が小さい。

### 難所3 — 「メロディが和音を決める」は依存が逆転する

アイドル/アニソンの「メロディのフックが先、和音が後から合わせる」（メロディの9thが `IVadd9` を要求する等）は、現行の**和音→メロディ**の依存を反転させます。

> **判断**: 全面的な反転は影響が大きすぎます。**現実解は「メロディ音を和音の使用可能テンションとして受け入れる」方向**——つまり和音生成後、メロディが非和声音に着地したら、その音をテンションとして**和音側に追記する**後処理。基盤Bの `tensions[]` があれば実装可能。

### 難所4 — 決定性との整合

現行の最大の美点は「同じシード＋設定なら必ず同じ曲」です。基盤A〜Cで選択肢が激増すると、**シードから決定的に選ぶ範囲**が広がります。

> **判断**: 既存の `deriveSeed(seed, "...", index)` パターンを踏襲すれば維持可能。ただし**テンプレート追加が既存シードの出力を変える**（`templates[random % length]` の length が変わるため）。
> **対策**: プリセットのテンプレート配列に**追記のみ**（既存要素の順序を変えない）とするか、テンプレートIDでハッシュして選ぶ方式に変え、配列長に依存させない。**後者を推奨**——これをやらないと、進行を1つ足すたびに既存の全楽曲が変わります。

### 難所5 — 検証（validation）の再設計

`validateComposition` は「和音は宣言された度数で説明できるか」を検査します。基盤A・Bを入れると:
- `♭II` の和音は現行の `degree: 1..7` に収まらない
- テンション付き和音の「正しさ」の定義が必要（アヴォイドノート判定など）
- スラッシュコードのベースは構成音でなくてよい

> **判断**: 検証は**ルールベースからスタイル依存のペナルティ**へ移行すべきです。調査で得た一次資料（SATB規則、ジャズヴォイシング）の両方が「これらは絶対法則ではなく様式内の慣習」と明記しており、**0/1の禁止ではなく重み付きスコア**が原典の姿勢に忠実です。

## 4. 実装順序の提案

依存関係と、各段階で「何が鳴らせるようになるか」で並べます。

| 段階 | 内容 | これで鳴るようになるもの | 規模 |
|---|---|---|---|
| **1** | 基盤A（進行テンプレート構造化）＋ UIで進行選択 | 王道/小室/丸サ/カノン/循環、`I–III7–vi`、♭系借用、経過減七 | 中 |
| **2** | 基盤B（`base+tensions`）＋ アヴォイドノート回避＋縮約ボイシング | 9/11/13、`6/9`、`maj9`、オルタード、city pop/lo-fi/R&B の質感 | 大 |
| **3** | スラッシュコード（`bass` フィールド＋ボイシング対応） | ブラックアダー、トレイン進行、カノン下降ベース、`FΔ/G` | 小〜中 |
| **4** | 基盤C（セクション構造）＋ 最終サビ転調 | アニソン/アイドルの構成、トラックドライバー転調 | 大 |
| **5** | 複調（melodyMode 分離）＋ ペンタトニック | 中田ヤスタカ、じんの旋律色 | 小 |
| **6** | 通作形式（repeat:false）＋ 非機能的シーケンス | artcore、田中秀和の aug 平行移動 | 中 |
| **7** | ボイスリーディング強化（スタイル別ペナルティ） | 導音解決・並行5度制御・開離配置 | 中 |

**段階1〜3で、調査した「名前付き進行」はほぼ全部鳴らせます。** 段階4以降は曲の構造とスタイルの再現度を上げる領域です。

## 5. 「全実装」に対する率直な評価

### やるべきでないこと

**すべてを1つの型で表現しようとすること。** 難所1で述べたとおり、機能和声の度数体系と非機能的な平行移動は**異なる生成原理**です。無理に統一すると、どちらも中途半端になります。

**進行データを闇雲に増やすこと。** 調査で判明したとおり、出典の多くはブログ水準で**誤ラベルが実在**しました（照合した4項目中3項目に誤り）。実装データに投入する前に原典照合が要ります。信頼できるのは:
- **一次データ**: [コード進行メモ倉庫](https://music-chord.com/) の実曲セクション別データ
- **実務者合意**: 複数の独立した作曲教室が同じ名前・同じ度数で挙げる進行（王道/小室/丸サ/カノン/循環）

### 現実的な「全実装」の定義

**「調査した名前付き進行と技法を、ユーザーが選んで鳴らせる状態」**を全実装と定義するなら、**段階1〜3（基盤A＋B＋スラッシュコード）で到達**します。ここが最もROIが高い区切りです。

段階4以降（セクション/転調/複調/通作形式）は「**進行の実装**」というより「**楽曲構造の実装**」であり、別プロジェクトとして扱う方が健全です。

### 最小で最大の効果を出すなら

**基盤Aだけ**を先に入れる。理由:
- 王道進行（学術的裏付けあり・5ジャンル共通・**現行 `ChordQuality` で表現可能**）が即座に載る
- 既存プリセットを機械変換でき、後方互換を壊さない
- ユーザー要望「コード進行を選んで生成」の直接の答え
- 段階2以降すべての土台になる

ただし**難所4（決定性）の対策を同時に入れること**。テンプレート選択を配列長に依存させない方式に変えないと、以後データを足すたびに既存楽曲が変わり続けます。
